# Bank module

Owner-only **Finance → Bank** (`/admin/bank`), following the existing Finance access rule. Bank is a separate ledger of raw bank movements. Importing never writes to Payments, payment splits, Cashier, clinic Finance, or Israeli Finance. There are no transfers, payment confirmations, bank credentials, API calls, or automatic payment matching.

## Local verification

1. Run `php artisan migrate` (the new migration has already been applied to this development database).
2. Log in as Owner, open **Finance → Bank**, and select **Import Statement**.
3. Upload the original BOG Business Online `.xlsx` or UTF-8 `.csv` without editing it. CSV accepts comma, semicolon or tab delimiters. Files are limited to 10 MB, 50,000 rows and 100 MB uncompressed workbook contents. Password-protected workbooks and legacy `.xls` are not supported.
4. The result opens the import batch, with account/currency, statement period, opening/closing balances, imported/duplicate/rejected counts and row errors. Imported original files are retained on the **private local disk**, under generated names; the original filename is preserved separately.
5. Use the date filters if the statement is outside the default last seven days. Select a row date or description to load identifiers and original row details. Click its category to open dependent Category/Subcategory selectors. **Finance > Expense Categories** manages the shared Cash/Bank hierarchy. See [Shared categories and Bank rules](shared-expense-categories.md).
6. Upload the same file again. Imported rows should be zero, duplicates should match the original accepted rows, and the original transaction records/categories should remain unchanged.
7. Open **Import history** to review either batch. Compare Cashier/Payments before and after: they must remain unchanged.
8. To undo a specific import as Owner, select its filename in **Import history**, then **Rollback Import**. The confirmation shows filename, period and current linked transaction count. Only rows owned by that batch are deleted. The original file, original counts/errors and rollback audit remain in history; the rolled-back balance snapshot is excluded from current balances.

Run focused tests with `php artisan test --compact tests/Feature/BankModuleTest.php`. They generate real `.xlsx` fixtures with title/metadata rows, Georgian/bilingual column headings, Excel serial dates, blanks, balances and identifiers. The retained original `Statement of Account` workbook has also been verified read-only: rows 14–95 produce 82 valid transactions (56 inflows, 26 outflows), zero rejected rows, and an unchanged file hash. A sanitized 82-row regression fixture includes the exact three reported opening transactions and the conflicting later turnover columns.

## Import and accounting semantics

- `BogStatementParser` scans the sheet for date/debit/credit headers rather than assuming a fixed row or requiring bank branding/operation identifiers. Regression fixtures cover the supplied `Statement of Account` structure with metadata above row 13 and transactions from row 14, as well as headers at row 50. English and Georgian aliases include `ოპერაციის იდ`, `მოკორესპოდენტო ანგარიში`, `ოპერაციის შინაარსი` and `ნაშთი ოპერაციის ბოლოს`. Bilingual headers can contain slash/newline separators. Blank or whitespace-only debit/credit cells are optional; the populated positive side determines direction and amount. Signed `თანხა` and conversion columns never override debit/credit. All original cells, including `საბუთის N` and both debit/credit values, remain in `raw_data`.
- Dates are parsed strictly, including styled dates and numeric Excel serials using the workbook's 1900/1904 calendar. Monetary values become two-decimal strings. Unsupported precision, ambiguous directions, malformed dates and invalid currencies are rejected rather than coerced to zero or today.
- Invalid rows in an otherwise recognized statement are skipped **and explicitly reported**. Movement totals only include accepted rows. A file with no valid recognized transactions fails entirely. Metadata conflicts or transaction ID conflicts also fail the entire import. The batch and all accepted transactions commit together.
- `BankTransactionData` is the common normalized input. `BankStatementRows` spools normalized rows to a temporary stream (spilling to disk above 2 MB), so original/raw rows are not all retained in PHP memory. Ingestion processes 250 rows at a time. Temporary storage is automatically removed.
- Operation identity is scoped to bank + account + currency + operation ID. Without an ID, a stable fingerprint uses the account, date, direction, amount, currency, type, reference, counterparty and purpose. Neither the filename nor the row number contributes to identity. The database enforces a unique deduplication key. Existing rows are never overwritten. A repeated ID with conflicting date/direction/amount causes rollback. Identical transactions without distinguishing IDs/reference/details are inherently indistinguishable and will deduplicate; review such cases against the statement.
- `bank_fee` and `gross_amount` retain explicit source values. COM debits default to Bank fee / expense; the Fees card counts their transaction amount once even if `bank_fee` repeats that amount. PBS defaults to Cash deposit / transfer. TRN credits default to Card settlement only for explicit settlement wording or the verified BOG card-brand plus POS-terminal pattern. PMD has no blanket expense default. No currency conversion occurs.
- Balance cards show individual account/currency balances and their dates. The newest reliable dated statement provides the balance directly, without adding later raw movements. Explicit openings are a labelled fallback only until a statement exists. An older statement uploaded later cannot replace a newer statement. An explicit statement closing balance requires an explicit period-end date and a unique account/currency. Otherwise a running balance is used only when statement ordering can be established by matching consecutive balances to movements. Missing/ambiguous data displays “—”. Balances are independent of movement filters except currency and are explicitly labeled as imported, not live.
- Categories have stable IDs. Deactivation prevents new assignments while existing assignments retain their labels. Referenced categories are protected by restrictive foreign keys; the UI offers deactivation instead of deletion.

## Performance and future API integration

The original Bank render used six Bank SQL reads (shared category/subcategory selectors now add two fixed dimension reads): paginated row count + 25 rows, one grouped SUM for all three movement cards, one window query for latest account balances, one distinct filter-options query, and one categories query. No per-row relationship queries. Raw rows and batch errors are omitted from initial page data and loaded only when details/history are opened. No persistent cache is added.

A future API adapter should produce `BankTransactionData` and call `BankIngestionService::ingest($rows, 'api')`; the existing table, category assignments, movement filters and totals already accept either source. A future live-balance provider can extend the separate balance-reporting method; no live balance is claimed today. Cash/Bank/All P&L uses explicit accounting treatments and the Owner's Already recorded in ERP flag; it does not perform automatic matching.

## Accounting classification and P&L

- Run `php artisan migrate`, then `php artisan bank:classify-uncategorized` to classify existing unassigned imports. The command and Owner **Categorization rules → Apply to Uncategorized** action use the same service. They preserve manual choices, ERP flags and raw movement facts. Imports use two fixed category/rule reads per ingestion, with no rule query per row. Backfills use chunks of 250 without loading raw JSON.
- `2026_09_11_230000_add_bank_accounting.php` adds stable category codes, editable accounting treatments, transaction exclusion/fee/provenance flags and simple phrase rules. Existing category assignments are marked manual. Categories and rules are Owner-managed; inactive categories are unavailable for new assignments/rules, while historical classification remains readable and effective.
- Internal movement codes retain accounting treatments. User-managed expense categories/subcategories are shared with Cash. Safe BOG defaults run first; otherwise rules prefer exact normalized company plus keyword, company default, then description keyword. Equally specific conflicting targets remain Uncategorized. Deleting/deactivating a rule does not erase existing classifications. A manual selection or manual clearing is persistent, including across duplicate imports and backfills.
- **Already recorded in ERP** in transaction details excludes only Bank P&L. It changes neither Bank Inflow/Outflow nor the statement balance. No Finance record is created by categorization.
- Gross and commission metadata are extracted from dedicated columns or explicit same-currency BOG description labels. A settlement fee is automatic when gross minus credit equals the fee; a corresponding standalone COM takes precedence to avoid duplication. Ambiguous annotations remain informational. For an explicitly classified settlement with a reported `bank_fee`, Owner can opt in to **Include withheld fee as an expense** under Additional details for an ambiguous annotation, only after confirming the withheld cost. Changing its category clears this opt-in. The flag does not change movement totals. Contradictory COM credits are preserved as raw credits and left unclassified rather than silently reversing direction.
- Main Finance and the separate **Profit & Loss** report (`/admin/profit-loss`) show Revenue, Expenses and Profit with dates, period, money source and currency. “Cash” means the existing ERP ledger, including canonical patient card payments; the UI explains this explicitly. “Bank” contributes classified, non-excluded expenses only. “All” combines those sources without including card settlements/deposits/transfers as revenue. Both use the same normalized SQL ledger. Manual Pre-cutover / Legacy flags exclude Bank P&L while retaining movement and balance contributions.
- `ProfitLossReport` performs one SQL `UNION ALL` + `SUM/GROUP BY` query: non-deleted Payments via PaymentSplits, product sales, partner patient payments, FinanceTransactions, independent Israeli expense transactions, and eligible Bank rows. Salary reversal postings reduce expenses instead of creating revenue; linked salary cash allocations are not counted twice. Revenue uses ERP records only; imported credits do not create revenue. Bank expenses use expense and Uncategorized outflows plus confirmed withheld commissions; known transfers and settlements remain excluded. Currencies stay separate; this is payment-based P&L, with no accrual/depreciation engine.
- Bank selectors add two fixed shared-dimension reads to the original six Bank reads; the fee/category join adds no query. P&L runs one aggregate for all three cards. Rule management eagerly loads categories. No persistent cache, hover requests, API writes, automatic payment matching or additional Cashier writes are introduced.
- New implementation files: `BankAccounting`, `BankClassificationService`, `ProfitLossReport`, `BankCategorizationRule`, `ClassifyBankTransactions`, `BankRules`, `ProfitLoss`, their Blade views, `lang/{en,ka}/bank-accounting.php`, and `tests/Feature/BankAccountingTest.php`. Existing Bank report/ingestion/page/category files and the Finance header are integrated with them.

Run `php artisan test --compact tests/Feature/BankModuleTest.php tests/Feature/BankAccountingTest.php` for import, accounting, access, P&L source/date boundaries, duplicate-control and query-count regressions.

## Windows upload failure correction

The reported small-file failure was reproduced over the real HTTP endpoint: a 48,657-byte valid XLSX returned HTTP 422 with `PHP Request Startup: File upload error - unable to create a temporary file`. `artisan serve` removed `TEMP`/`TMP` from the worker environment, causing PHP (with no explicit `upload_tmp_dir`) to fall back to unwritable `C:\WINDOWS`. Laravel's log had no upload exception because the failure occurred during PHP request startup.

`AppServiceProvider` now adds `TEMP`, `TMP`, and `TMPDIR` to Laravel's Windows console server environment allowlist. Restart `php artisan serve` after pulling this change. The local server has already been restarted and the same HTTP probe now returns 200. Livewire's effective temporary disk remains `local`, with writable `storage/app/private/livewire-tmp`; no global MIME restrictions or disk overrides were needed.

The Bank field also now supports Excel/CSV MIME aliases, explicit extension validation and Filament's browser extension-to-MIME mapping. ZIP/octet-stream MIME results are accepted only alongside an allowed filename extension; the parser still validates workbook structure before ingestion. Files remain privately stored with random names before the import action reads them. No `storeFiles(false)` or ephemeral-file handoff is used.

The installed PHP configuration currently limits individual HTTP uploads to 2 MB (`upload_max_filesize`), below the form's 10 MB maximum; this did not cause the 47 KB failure. Larger uploads require matching PHP upload/post limits and a server restart.

## Transaction / turnover column mapping correction

The original workbook exposed a mapping collision: `ბრუნვა დებეტი` and `ბრუნვა კრედიტი` were incorrectly listed as aliases for transaction debit/credit. The mapping loop overwrote D/E (zero-based 3/4) with W/X (22/23). Rows 14–16 consequently read summary values 2569.70 and 1507.94 on both sides. This was not an off-by-one error or a defect in the source's blank cells.

Turnover aliases have been removed. Header mapping preserves the first exact alias match, preventing later detail columns from replacing an existing mapping. Verified positions are A=0 (date), D=3 (debit), E=4 (credit), G=6 (type), H=7 (operation ID), I=8 (Ref). Validation uses explicit positive-side flags and rejects when both flags are equal. Signed amount and conversion columns do not determine direction.

The initial read-only audit found 21 previously imported records with amounts/directions inconsistent with the corrected parsing. Diagnostic output is local-only in `storage/app/bog-mapping-diagnostic.json`; no ongoing production row logging was added.

At the user's explicit request, faulty batch #1 (`St_ST_20260904_20260911.xlsx`, GEL, 04.09.2026–11.09.2026) was subsequently recovered. A private backup of its batch and 21 original transactions was saved under `storage/app/private/bank-recovery/batch-1-before-rollback-20260911-131813.json`. In one database transaction, only its 21 linked rows were deleted, batch #1 was marked rolled back, and the unchanged original workbook was re-imported into batch #3: **82 imported, 0 duplicates, 0 rejected; 56 inflows and 26 outflows**. Snapshot comparisons verified that other Bank batches/rows, categories, Cashier, Payments and Finance data were unchanged. Normal operation-ID duplicate/conflict validation remains strict.
